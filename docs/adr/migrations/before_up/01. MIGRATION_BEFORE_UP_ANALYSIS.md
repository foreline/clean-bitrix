# Migration Before Up — Analysis & Implementation Proposal

**Date:** 2026-03-17
**Status:** Draft
**Priority:** HIGH
**Related:** [00. MIGRATION_BEFORE_UP_PROPOSAL.md](00.%20MIGRATION_BEFORE_UP_PROPOSAL.md)

---

## Context

When a developer refactors the codebase and changes namespace structures, the corresponding `EntityTable` classes change their table names (via `getTableName()`). Running `EntityTable::checkTable()` in this situation creates a brand-new table under the new name, leaving the old table with existing data untouched. This results in data loss and orphaned tables.

The migration framework currently has no mechanism to execute preparatory actions (such as table renaming) **before** `EntityTable::checkTable()` is called.

## Current Migration Lifecycle

```
MigrationManager::executeMigration()
│
├─ connection->startTransaction()
├─ migration->validate($connection)         ← precondition checks
├─ migration->up($connection, $logger)
│  │
│  ├─ foreach $entityTables:                ← Step 1
│  │  └─ EntityTableClass::checkTable()
│  │     ├─ createTable()                   ← creates table if missing
│  │     └─ updateTable()                   ← syncs fields, indexes, constraints
│  │
│  └─ foreach $customUpSql:                 ← Step 2
│     └─ connection->query($sql)
│
├─ MigrationVersionTable::add()             ← record execution
└─ connection->commitTransaction()
```

### The Problem

The `up()` method in `AbstractMigration` has two steps:
1. Call `EntityTable::checkTable()` for each entity table class
2. Execute custom SQL statements

There is **no step before** the entity table checks. When namespaces change:

1. `OldNamespace\SomeTable::getTableName()` returned `old_table_name`
2. `NewNamespace\SomeTable::getTableName()` returns `new_table_name`
3. `checkTable()` sees `new_table_name` doesn't exist → creates it empty
4. `old_table_name` still exists with all the data → orphaned

**Source files analyzed:**
- `src/Infrastructure/Repository/Migration/MigrationInterface.php` — defines `up()`, `down()`, `validate()`
- `src/Infrastructure/Repository/Migration/AbstractMigration.php` — implements the two-step `up()` flow
- `src/Infrastructure/Repository/Migration/MigrationManager.php` — transaction wrapper, version tracking
- `src/Infrastructure/Repository/Migration/MigrationVersionTable.php` — applied migration storage
- `src/Infrastructure/Bitrix/Repository/ORM/OrmDataManager.php` — `checkTable()`, `createTable()`, `updateTable()` implementation

## Proposed Solution

### Architecture: Template Method Pattern

Add `beforeUp()` and `beforeDown()` lifecycle hooks to `AbstractMigration` using the Template Method pattern. These are protected methods that subclasses override when they need pre-migration actions.

This approach:
- Follows Open/Closed Principle — existing migrations are unaffected
- Requires zero changes to `MigrationInterface` — stays backward-compatible
- Keeps `MigrationManager` untouched — the hooks are internal to `AbstractMigration`
- Uses a pattern already established in the codebase (`validate()` as an overridable hook)

### New Migration Lifecycle

```
migration->up($connection, $logger)
│
├─ beforeUp($connection)                    ← NEW: pre-migration hook
│  ├─ renameTable(old, new)                 ← e.g., table renaming
│  ├─ custom data transformations
│  └─ any preparatory SQL
│
├─ foreach $entityTables:                   ← Step 1 (unchanged)
│  └─ EntityTableClass::checkTable()
│
└─ foreach $customUpSql:                    ← Step 2 (unchanged)
   └─ connection->query($sql)
```

```
migration->down($connection, $logger)
│
├─ beforeDown($connection)                  ← NEW: pre-rollback hook
│  ├─ renameTable(new, old)                 ← e.g., reverse the rename
│  └─ any preparatory SQL
│
└─ foreach $customDownSql (reversed):       ← existing rollback logic
   └─ connection->query($sql)
```

## Implementation Details

### 1. Changes to `AbstractMigration`

Add two protected template methods and a `renameTable()` helper:

```php
<?php
declare(strict_types=1);

namespace Infrastructure\Repository\Migration;

use Bitrix\Main\DB\Connection;
use Bitrix\Main\DB\SqlQueryException;
use Exception;
use Psr\Log\LoggerInterface;

abstract class AbstractMigration implements MigrationInterface
{
    protected ?LoggerInterface $logger = null;

    /** @var array<string> */
    protected array $entityTables = [];

    /** @var array<string> */
    protected array $customUpSql = [];

    /** @var array<string> */
    protected array $customDownSql = [];

    abstract public function getVersion(): string;
    abstract public function getDescription(): string;

    /**
     * Apply migration using EntityTable checkTable method
     * @throws Exception
     */
    public function up(Connection $connection, ?LoggerInterface $logger = null): void
    {
        $this->logger = $logger;

        // NEW: Execute pre-migration actions (table renames, data prep, etc.)
        $this->beforeUp($connection);

        // Step 1: Apply entity table migrations
        foreach ($this->entityTables as $entityTableClass) {
            $this->logger?->info("Checking table for: {$entityTableClass}");

            if (!class_exists($entityTableClass)) {
                throw new Exception("Entity table class not found: {$entityTableClass}");
            }

            if (!method_exists($entityTableClass, 'checkTable')) {
                throw new Exception("Class {$entityTableClass} does not have checkTable method");
            }

            $entityTableClass::checkTable($logger);
        }

        // Step 2: Execute custom SQL
        foreach ($this->customUpSql as $sql) {
            $this->logger?->info("Executing custom SQL: {$sql}");

            try {
                $connection->query($sql);
            } catch (SqlQueryException $e) {
                $this->logger?->error("SQL execution failed: " . $e->getMessage());
                throw $e;
            }
        }
    }

    /**
     * Rollback migration
     */
    public function down(Connection $connection, ?LoggerInterface $logger = null): void
    {
        $this->logger = $logger;

        // NEW: Execute pre-rollback actions
        $this->beforeDown($connection);

        // Execute rollback SQL in reverse order
        $downSql = array_reverse($this->customDownSql);

        foreach ($downSql as $sql) {
            $this->logger?->info("Executing rollback SQL: {$sql}");

            try {
                $connection->query($sql);
            } catch (SqlQueryException $e) {
                $this->logger?->error("Rollback SQL execution failed: " . $e->getMessage());
                throw $e;
            }
        }

        $this->logger?->warning(
            "Entity tables are not automatically dropped during rollback. " .
            "Manual intervention may be required."
        );
    }

    // ... validate(), tableExists(), columnExists(), indexExists() unchanged ...

    /**
     * Hook: actions to perform BEFORE entity table checks in up()
     *
     * Override in concrete migrations to rename tables, transform data,
     * or perform any preparatory work before EntityTable::checkTable() runs.
     *
     * This method runs inside the MigrationManager transaction.
     */
    protected function beforeUp(Connection $connection): void
    {
        // No-op by default. Override in subclasses.
    }

    /**
     * Hook: actions to perform BEFORE rollback SQL in down()
     *
     * Override in concrete migrations to reverse any preparatory work
     * done in beforeUp().
     *
     * This method runs inside the MigrationManager transaction.
     */
    protected function beforeDown(Connection $connection): void
    {
        // No-op by default. Override in subclasses.
    }

    /**
     * Helper: Rename a database table safely.
     *
     * Handles four scenarios:
     *   1. Old table exists, new doesn't   → RENAME TABLE (normal case)
     *   2. Old doesn't exist, new exists   → skip (already renamed)
     *   3. Both exist                      → throw exception (conflict)
     *   4. Neither exists                  → skip (nothing to do)
     *
     * @param Connection $connection Database connection
     * @param string $oldTableName Current table name
     * @param string $newTableName Desired table name
     * @throws Exception When both old and new tables exist (conflict)
     * @throws SqlQueryException On SQL execution failure
     */
    protected function renameTable(
        Connection $connection,
        string $oldTableName,
        string $newTableName,
    ): void {
        $oldExists = $connection->isTableExists($oldTableName);
        $newExists = $connection->isTableExists($newTableName);

        if ($oldExists && $newExists) {
            throw new Exception(
                "Cannot rename table `{$oldTableName}` to `{$newTableName}`: " .
                "both tables already exist. Manual resolution required."
            );
        }

        if (!$oldExists && $newExists) {
            $this->logger?->info(
                "Table `{$newTableName}` already exists, skipping rename from `{$oldTableName}`"
            );
            return;
        }

        if (!$oldExists && !$newExists) {
            $this->logger?->info(
                "Neither `{$oldTableName}` nor `{$newTableName}` exist, skipping rename"
            );
            return;
        }

        // oldExists && !newExists → perform rename
        $sql = "RENAME TABLE `{$oldTableName}` TO `{$newTableName}`";
        $this->logger?->info($sql);
        $connection->query($sql);
    }
}
```

### 2. Table Renaming Design

The `renameTable()` helper method is designed to be **idempotent and safe**:

| Old Table | New Table | Action | Rationale |
|-----------|-----------|--------|-----------|
| Exists | Doesn't exist | `RENAME TABLE` | Normal migration scenario |
| Doesn't exist | Exists | Skip (log info) | Migration already applied / re-run safe |
| Both exist | Both exist | **Throw exception** | Ambiguous state, requires manual resolution |
| Neither exists | Neither exists | Skip (log info) | Fresh install, nothing to rename |

**Why `RENAME TABLE` over other approaches:**
- **Atomic in MySQL/MariaDB** — no intermediate state where the table is missing
- **Preserves all data, indexes, triggers, auto-increment values** — zero data loss
- **Preserves foreign key references** — InnoDB updates internal references automatically
- **Fastest possible operation** — metadata-only change, no data copying
- **Works within transactions** — compatible with `MigrationManager`'s transaction wrapper

**Database compatibility notes:**
- MySQL 5.7+ / MariaDB 10.2+: Full support for `RENAME TABLE`
- The Bitrix framework targets MySQL/MariaDB exclusively, so cross-database compatibility (PostgreSQL, SQLite) is not a concern
- If future DB support is needed, `renameTable()` can be overridden in a DB-specific subclass

### 3. No Changes Required to Other Components

| Component | Changes | Reason |
|-----------|---------|--------|
| `MigrationInterface` | None | `beforeUp`/`beforeDown` are implementation details of `AbstractMigration`, not contract requirements |
| `MigrationManager` | None | It calls `up()`/`down()` which internally call hooks — transparent to the manager |
| `MigrationVersionTable` | None | Version tracking is unaffected |
| `OrmDataManager` | None | `checkTable()` behavior is unchanged; it simply benefits from the table being pre-renamed |

## Usage Example

### Scenario: Namespace Refactoring

A developer moved `ServiceDesk\Ticket\TicketTable` (table name: `servicedesk_tickets`) to `Support\Ticket\TicketTable` (table name: `support_tickets`).

```php
<?php
declare(strict_types=1);

namespace Migrations;

use Bitrix\Main\DB\Connection;
use Infrastructure\Repository\Migration\AbstractMigration;
use Support\Ticket\TicketTable;
use Support\Ticket\TicketCommentTable;

class Version20260317120000 extends AbstractMigration
{
    protected array $entityTables = [
        TicketTable::class,
        TicketCommentTable::class,
    ];

    public function getVersion(): string
    {
        return '20260317120000';
    }

    public function getDescription(): string
    {
        return 'Rename ServiceDesk tables to Support namespace';
    }

    /**
     * Rename old tables BEFORE checkTable() creates new ones
     */
    protected function beforeUp(Connection $connection): void
    {
        $this->renameTable($connection, 'servicedesk_tickets', 'support_tickets');
        $this->renameTable($connection, 'servicedesk_ticket_comments', 'support_ticket_comments');
    }

    /**
     * Reverse the rename on rollback
     */
    protected function beforeDown(Connection $connection): void
    {
        $this->renameTable($connection, 'support_tickets', 'servicedesk_tickets');
        $this->renameTable($connection, 'support_ticket_comments', 'servicedesk_ticket_comments');
    }
}
```

**What happens when this migration runs:**

1. `MigrationManager::executeMigration()` starts a transaction
2. `validate()` checks that entity classes exist
3. `up()` is called:
   - `beforeUp()` renames `servicedesk_tickets` → `support_tickets`
   - `beforeUp()` renames `servicedesk_ticket_comments` → `support_ticket_comments`
   - `TicketTable::checkTable()` finds `support_tickets` already exists → syncs fields/indexes
   - `TicketCommentTable::checkTable()` finds `support_ticket_comments` already exists → syncs fields/indexes
4. Version is recorded, transaction committed

**On rollback:**

1. `down()` is called:
   - `beforeDown()` renames tables back to old names
   - Warning logged about manual table cleanup
2. Version record removed

### Scenario: Fresh Install (No Old Tables)

The same migration on a fresh installation (where `servicedesk_*` tables never existed):

1. `beforeUp()` calls `renameTable()` — neither table exists → **skip** (logged)
2. `checkTable()` creates `support_tickets` from scratch
3. Migration completes normally

This idempotent behavior means the same migration works for both upgrades and fresh installs.

## Alternatives Considered

### Alternative 1: Array-Based Hooks (`$beforeUpSql`)

```php
protected array $beforeUpSql = [
    "RENAME TABLE `old_table` TO `new_table`",
];
```

**Rejected because:**
- Cannot express conditional logic (e.g., "only rename if old table exists")
- Would fail on fresh installs where old tables don't exist
- Duplicates the pattern of `$customUpSql` without adding value
- Cannot handle the four-scenario safety matrix (exists/doesn't exist)

### Alternative 2: Add Methods to `MigrationInterface`

```php
interface MigrationInterface
{
    public function beforeUp(Connection $connection): void;
    public function beforeDown(Connection $connection): void;
    // ... existing methods
}
```

**Rejected because:**
- **Breaking change** — all existing `MigrationInterface` implementations would need updating
- Forces every migration to implement methods they don't need
- The hooks are an implementation detail, not a contract requirement
- `validate()` already exists as an overridable hook on `AbstractMigration`, establishing the pattern

### Alternative 3: Hook in `MigrationManager`

```php
// In MigrationManager::executeMigration()
if ($migration instanceof BeforeUpAwareInterface) {
    $migration->beforeUp($this->connection);
}
```

**Rejected because:**
- Adds complexity to `MigrationManager` which should remain a simple orchestrator
- Introduces a new interface for a feature that naturally belongs in the base class
- The Template Method pattern in `AbstractMigration` achieves the same result more elegantly

### Alternative 4: Modify `OrmDataManager::checkTable()` to Accept Rename Map

```php
public static function checkTable(?LoggerInterface $logger = null, array $renames = []): void
```

**Rejected because:**
- Couples table renaming logic to the ORM layer, violating separation of concerns
- `OrmDataManager` should only care about schema synchronization, not migration orchestration
- Changes the signature of a widely-used method

## Implementation Plan

### Phase 1: Core Implementation
1. Add `beforeUp()` and `beforeDown()` protected methods to `AbstractMigration`
2. Modify `AbstractMigration::up()` to call `beforeUp()` before the entity table loop
3. Modify `AbstractMigration::down()` to call `beforeDown()` before the rollback SQL loop
4. Add `renameTable()` helper method to `AbstractMigration`

### Phase 2: Testing
1. Unit test: `beforeUp()` is called before `checkTable()`
2. Unit test: `beforeDown()` is called before rollback SQL
3. Unit test: `renameTable()` handles all four scenarios correctly
4. Unit test: Migration with `beforeUp()` works in transaction (rollback on failure)
5. Integration test: Full namespace refactoring scenario with real tables

### Phase 3: Documentation
1. Update `README.md` migration section with `beforeUp`/`beforeDown` usage
2. Add example migration to documentation

## Success Criteria

- [ ] `beforeUp()` executes before any `EntityTable::checkTable()` call
- [ ] `beforeDown()` executes before any rollback SQL
- [ ] `renameTable()` is idempotent (safe to run multiple times)
- [ ] `renameTable()` throws on ambiguous state (both tables exist)
- [ ] Existing migrations continue to work without any changes
- [ ] No changes to `MigrationInterface`, `MigrationManager`, or `OrmDataManager`
- [ ] PHPStan passes at level 0
- [ ] PHPUnit tests pass
